# اعتبار تومانی و حسابرسی مصرف

## مدیریت کاربران

با مدیر ساخته‌شده توسط `createsuperuser` وارد `/admin/` شوید. از بخش احراز هویت، **کاربران ← افزودن کاربر** را باز کنید. نام کاربری و رمز عبور را وارد کنید، نقش را انتخاب کنید و برای دسترسی فوری، «فعال» را علامت بزنید.

| انتخاب فرم | دسترسی |
| --- | --- |
| **User — کاربر** | ورود به پورتال، گفتگو با مدل‌های فعال، مشاهدهٔ تاریخچه و اعتبار خودش |
| **Admin — مدیر** | همهٔ امکانات کاربر، پنل Django، ساخت مدیر یا کاربر، مدیریت مدل‌ها، اتصال‌ها، اعتبار و گزارش مصرف |

نقش Admin هر دو پرچم استاندارد `is_staff` و `is_superuser` را فعال می‌کند. نقش User هر دو را غیرفعال می‌کند. حساب‌های قدیمی که فقط یکی از پرچم‌ها را دارند، تا تعیین صریح نقش Admin، در پورتال دسترسی کاربر عادی دارند. مدیر می‌تواند اطلاعات شخصی یا نقش را در صفحهٔ همان کاربر و رمز را از پیوند تغییر رمز Django ویرایش کند.

### غیرفعال‌سازی و فعال‌سازی مجدد

در صفحهٔ کاربر، علامت **فعال** را بردارید و ذخیره کنید. فهرست کاربران وضعیت فعال را نشان می‌دهد و فیلتر فعال/غیرفعال دارد. پس از ثبت تغییر، ورود جدید و دسترسی نشست جاری به APIهای محافظت‌شده مسدود می‌شود. Django وضعیت کاربر را در هر درخواست از پایگاه داده می‌خواند. برای بازگرداندن دسترسی، «فعال» را دوباره علامت بزنید. نشست قبلی که هنوز معتبر است ممکن است پس از فعال‌سازی مجدد قابل استفاده باشد.

غیرفعال‌سازی از پنل برای ارسال‌های در حال اجرا درخواست توقف ثبت می‌کند. ناظر جریان هر ۰٫۷۵ ثانیه وضعیت توقف را بررسی می‌کند. دادهٔ از قبل ارسال‌شده یا در مسیر ممکن است به مرورگر برسد. پاسخ تکمیل‌شده محفوظ است و مدل در حال تولید با همان سیاست Stop تسویه می‌شود. متن جزئی مجاز و مصرف گزارش‌شده یا برآوردی ثبت و رزرو آزاد می‌شود. زمان قطع اتصال لزوماً با پایان هزینه در سرویس خارجی یکسان نیست. فعال‌سازی فوری یک ارسال متوقف‌شده را از سر نمی‌گیرد.

Account و آمار مصرف پس از غیرفعال‌سازی باقی می‌مانند. سیاست عادی ۳۰روزهٔ نگهداری گفتگوها برای حساب فعال و غیرفعال یکسان است.

## حساب و تعرفه

پایگاه داده و API پول را با عدد صحیح ریال نگه می‌دارند. فرم‌ها، گزارش CSV و صفحه‌های کاربری آن را به تومان نشان می‌دهند. یک ریال برابر ۰٫۱ تومان است. هر رکورد مدل در هر اتصال، دو تعرفهٔ فروش مستقل برای یک میلیون توکن ورودی و خروجی دارد. صفر تعرفهٔ رایگان است. هر دو تعرفه برای ارسال لازم‌اند. همگام‌سازی کاتالوگ فقط نام و فرادادهٔ مدل را تغییر می‌دهد.

مدیر در Django Admin در «تعرفه فروش» هر مدل، قیمت‌ها را به تومان وارد می‌کند. در «اعتبار پیش‌فرض کاربران جدید» می‌تواند یک مبلغ اولیه تعیین کند. پیش‌فرض نصب صفر است. در «افزودن کاربر» مبلغ صریح بر پیش‌فرض اولویت دارد. در صفحهٔ کاربر «تغییر اعتبار» و در فهرست کاربران اقدام گروهی «مدیریت اعتبار کاربران انتخاب‌شده» در دسترس است. افزایش، کاهش، تعیین اعتبار کل و بازپرداخت، دلیل و عامل دارند. برای بازپرداخت، شناسهٔ ردیف مصرف را از دفتر تراکنش‌ها بردارید. تراکنش تکراری با همان مرجع مالی فقط یک بار اثر می‌گذارد. مجموع بازپرداخت یک مصرف حداکثر برابر برداشت اصلی است.

پذیرش درخواست به اعتبار ریالی آزاد بستگی دارد. فیلد تاریخی `token_limit` برای سازگاری پایگاه داده و مشتریان API باقی مانده است. ویرایش حساب یا کاربر مقدار آن را تغییر نمی‌دهد. `tokens_used` شمارندهٔ مصرف است. ظرفیت Context و سقف خروجی هر مدل هنگام ارسال جداگانه بررسی می‌شوند.

| مقدار Account | معنا |
|---|---|
| credit_limit_rial | مجموع علامت‌دار تخصیص، اعتبار اولیهٔ مهاجرت و اصلاح سقف |
| credit_used_rial | مجموع برداشت مصرف منهای بازپرداخت |
| credit_remaining_rial | اعتبار کل منهای مصرف خالص، محاسبه‌شده در API |
| credit_reserved_rial | مجموع رزرو پاسخ‌های باز |
| credit_available_rial | مانده منهای رزرو، محاسبه‌شده در API |
| credit_version | نسخهٔ افزایشی حساب برای مرتب‌کردن عکس‌های موجودی در مرورگر |

«تنظیم» مقدار اعتبار کل را مشخص می‌کند. کاهش و تنظیم باید تمام مصرف خالص و رزروهای باز را پوشش دهند. بازپرداخت مصرف خالص را کم می‌کند. در گزارش مدل‌ها هزینهٔ برداشت‌شده از روی رویدادهای مصرف جمع می‌شود؛ بازپرداخت جداگانه در دفتر قابل مشاهده است. تخصیص اعتبار، جریان وجه نقد یا درآمد فروش محسوب نمی‌شود. قراردادهای مالی واقعی Provider، نرخ ارز، مالیات و پرداخت آنلاین در این نسخه مدل نشده‌اند.

## رزرو و تسویه

۱. مسیرهای JSON و SSE برای هر سؤال، از جمله نسخهٔ ویرایش‌شده، از پذیرش مشترک استفاده می‌کنند. در یک تراکنش کوتاه، سطر Account قفل می‌شود. Backend تاریخچهٔ فعال همان مدل، استدلال بازفرستاده‌شده، حاشیهٔ پیام و سقف معتبر خروجی را محاسبه می‌کند. بودجهٔ Thinking بخشی از خروجی مجاز است. فرمول برای هر پاسخ یک بار به ریال رو به بالا گرد می‌شود.

```text
هزینه = (ورودی × تعرفه ورودی + خروجی × تعرفه خروجی + ۹۹۹۹۹۹) // ۱۰۰۰۰۰۰
```

۲. پذیرش هزینهٔ سقف تک‌تک مدل‌ها را جمع می‌کند. اگر رزرو کامل از موجودی آزاد بیشتر باشد، برای مدل‌های تأییدشده سقف قابل پرداخت محاسبه می‌شود. اگر حتی حداقل خروجی معتبر قابل پرداخت نباشد، کل ارسال پیش از تماس رد می‌شود. در غیر این صورت، رزرو روی حساب و هر پاسخ ذخیره می‌شود. تعرفه‌ها روی همان پاسخ ثابت می‌شوند. تماس شبکه پس از آزادشدن قفل انجام می‌گیرد. بررسی برآورد فراخوانی Provider، رزرو یا رویداد مصرف ایجاد نمی‌کند.

۳. تسویهٔ هر پاسخ با ترتیب قفل حساب و سپس نوبت گفتگو انجام می‌شود. وضعیت نهایی پاسخ، آزادسازی کل رزرو آن، برداشت، رویداد مصرف و آمار مادام‌العمر User × Model در یک تراکنش ثبت می‌شوند. وضعیت پایانی و قید یکتای شناسهٔ پاسخ، تسویهٔ مجدد را محدود می‌کنند. مرور شاخه‌های گفتگو عملیات مالی ایجاد نمی‌کند.

۴. مبلغ برداشت برابر کوچک‌ترِ هزینهٔ محاسبه‌شده و رزرو است. دفتر، هر دو مبلغ و اختلاف پوشش‌نداده را نگه می‌دارد. هشدار عملیاتی فقط شناسهٔ پاسخ و اختلاف ریالی را ثبت می‌کند. این اختلاف بر مبنای تعرفهٔ فروش سامانه است.

| وضعیت Usage | سیاست |
|---|---|
| تفکیک معتبر Provider | ورودی و خروجی گزارش‌شده؛ توکن استدلال زیرمجموعهٔ خروجی است |
| فقط کل توکن | برای سهم معلوم استدلال، تعرفه خروجی؛ برای بقیه، ارزان‌ترِ دو تعرفه. منبع مالی تفکیک‌نشده «ناقص» است |
| بخشی از مصرف یا متن موجود | دادهٔ معتبر حفظ می‌شود. با متن قابل اندازه‌گیری، سمت مفقود مطابق تخمین موجود محاسبه می‌شود. با گزارش ناقص بدون متن، تنها حد پایین شناخته‌شده محاسبه می‌شود |
| صفر گزارش‌شده | صفر ثبت و رزرو آزاد می‌شود |
| هیچ گزارش یا متن قابل اندازه‌گیری | برداشت فعلی صفر، هزینهٔ محاسبه‌شده و هزینهٔ پاسخ تهی، وضعیت «نیازمند بررسی» |
| Stop، خطا یا قطع مرورگر | همان سیاست مصرف واقعی/ناقص/تخمینی اعمال می‌شود. Stop لزوماً هزینهٔ بیرونی را متوقف نمی‌کند |
| قطع Worker | پس از انقضای اجاره، cleanup یا `recover_reservations` رزرو را آزاد و رویداد نامشخص ثبت می‌کند. نویسندهٔ دیرهنگام نمی‌تواند آن را دوباره تسویه کند |

برای نمونه با ۲۰۰۰ توکن ورودی و ۱۰۰۰ خروجی، تعرفه‌های ۱۵۰٬۰۰۰/۱٬۲۰۰٬۰۰۰ تومان و ۴۰٬۰۰۰/۱۶۰٬۰۰۰ تومان، هزینه‌های مستقل ۱۵۰۰ و ۲۴۰ تومان دارند. از ۵۰۰٬۰۰۰ تومان، ۴۹۸٬۲۶۰ تومان باقی می‌ماند.

### سقف خروجی متناسب با اعتبار

در Django Admin، بخش «بودجه و پروتکل گفتگو»ی مدل، فیلد «حداقل خروجی تأییدشده برای کاهش سقف» اختیاری است. پس از بررسی قرارداد سرویس، کمترین تعداد توکن خروجی معتبر برای آن مدل را وارد کنید. بعد از تغییر اتصال، مدل یا قرارداد API این مقدار را دوباره بررسی کنید. خالی بودن فیلد، سیاست رزرو کامل را حفظ می‌کند.

پذیرش در قفل حساب، ماندهٔ آزاد پس از رزروهای هم‌زمان را می‌خواند. ابتدا هزینهٔ ورودی و تاریخچه، حداقل مدل و بودجهٔ عددی انتخاب‌شدهٔ استدلال به‌علاوهٔ یک توکن خروجی لحاظ می‌شود. بودجهٔ مدل‌های تأییدنشده کامل باقی می‌ماند. اگر اعتبار برای سقف‌های کامل کافی نباشد، جست‌وجوی دودویی با حساب صحیح، سهم یکسانی از فاصلهٔ حداقل تا سقف هر مدل تأییدشده را در حد موجودی مالی انتخاب می‌کند. محاسبه و گرد کردن به ریال برای هر مدل جداست. مدل با خروجی رایگان به کاهش سقف نیاز ندارد.

هر دو مسیر JSON و SSE همین حد را در پارامتر واقعی `max_tokens` یا `max_completion_tokens` می‌فرستند. هنگام کاهش، مقدار `limited_output_tokens` با شروع مدل ارسال و همراه پاسخ نگهداری می‌شود. تسویه با مصرف و تعرفهٔ همان درخواست انجام می‌شود. اگر سرویس از سقف تجاوز کند، همان سیاست ثبت مازاد و محدودکردن برداشت به رزرو اعمال می‌شود. انتخاب حداقل باید حاشیهٔ لازم برای مدل‌های دارای استدلال ضمنی را نیز پوشش دهد.

مرورگر هنگام نوشتن پیام درخواست برآورد ارسال نمی‌کند. API برآورد برای کلاینت‌های قبلی همچنان برآورد سقف کامل را برمی‌گرداند. جزئیات هر کارت، تعرفهٔ زمان ارسال و مصرف گزارش‌شده، برآوردی یا نامعلوم را نشان می‌دهد. تعداد توکن‌های ورودی از کش، هنگامی که سرویس آن را معتبر و در محدودهٔ ورودی گزارش کند، زیرمجموعهٔ ورودی است و در هزینه دوباره جمع نمی‌شود.

## دفتر، نگهداری و گزارش

CreditTransaction برای هر تسویه یک رویداد پایدار با شناسهٔ درخواست و پاسخ، مدل، کاربر، تعرفه، منبع، وضعیت، آمار توکن، رزرو اولیه و مانده پس از ثبت دارد. افزایش و بازپرداخت علامت مثبت، برداشت علامت منفی و اصلاح سقف علامت اختلاف دارد. رزرو موقت در مجموع دفتر وارد نمی‌شود. گزارش بازهٔ زمانی از تاریخ ثبت تراکنش استفاده می‌کند. تاریخ در منطقهٔ زمانی Django تفسیر می‌شود. گزارش مقدار برداشت، تعداد درخواست و میانگین را برای همهٔ تسویه‌های فیلترشده نشان می‌دهد؛ تعداد هزینه‌های نامعلوم نیز جداست.

دفتر مستقل از Message و Conversation است. حذف گفتگو و پاک‌سازی ۳۰روزه، مبلغ یا آمار را تغییر نمی‌دهد. برای کاربر یا مدل دارای سابقهٔ مالی، کلید خارجی محافظت‌شده از حذف جلوگیری می‌کند؛ مدیر می‌تواند آن‌ها را غیرفعال کند. در صورت حذف حساب مدیری که فقط عامل تغییر حساب دیگری بوده، شناسهٔ عامل تهی می‌شود. متن سؤال، استدلال، پاسخ و کلید Provider در دفتر ذخیره نمی‌شوند. تغییرات مالی از فرم‌های مجاز Admin انجام می‌شوند. دسترسی مستقیم مدیریتی به PostgreSQL باید محدود و نسخهٔ پشتیبان دفتر با سیاست سازمان نگهداری شود.

از لینک داشبورد صفحهٔ اول Django Admin یا «گزارش مصرف» در پورتال وارد شوید. در نمای «کاربران» روی نام کاربر و در نمای «مدل‌ها» روی مدل کلیک کنید تا جدول **کاربر × مدل** محدود به همان انتخاب شود. فیلتر تاریخ، کاربر، مدل، اتصال، وضعیت و منبع، جمع و میانگین، نمودار و CSV در دسترس‌اند. نماهای روزانه، هفتگی و ماهانه از همان رویدادها استفاده می‌کنند. کاربران عادی در «گزارش مصرف» فقط گزارش مالی و تراکنش‌های خود را دارند. مقدار بودجهٔ استدلال در تنظیم مدل، پارامتر درخواست است. فیلدهای توکن قدیمی API برای سازگاری حفظ شده‌اند.

## قراردادهای HTTP

| مسیر زیر /api/ | کاربرد |
|---|---|
| GET auth/me/ | مانده، مصرف، رزرو، اعتبار قابل استفاده و نسخهٔ حساب احراز هویت‌شده |
| GET models/ | تعرفهٔ فروش ورودی و خروجی هر رکورد مدل به ریال |
| POST credits/estimate/ یا conversations/{id}/estimate/ | همان ورودی ارسال سؤال؛ required_rial، available_rial و رزرو پیشنهادی تفکیکی |
| GET credits/{transactions,usage,trend}/report/ | دفتر، مصرف مدل و روند مالی شخصی |
| GET credits/summary/report/ | هزینهٔ برداشت‌شدهٔ امروز و ماه تقویمی میلادی جاری در منطقهٔ زمانی Django، فقط برای صاحب نشست |
| GET admin/billing/{summary,users,models,user-model-usage,transactions,trend}/ | گزارش مدیر فعال با هر دو پرچم staff و superuser |
| GET conversations/{id}/ و POST قدیمی | در هر پاسخ cost_rial، billing_source، billing_status و free_tariff |

گزارش‌های جدولی `page`، `size` تا ۱۰۰، `from` و `to` با تاریخ ISO، `model`، `status`، `source` و `export=csv` را می‌پذیرند. فیلتر مدیر شامل `user`، `q` (نام کاربری)، `provider` و `connection` هم هست. در جدول مصرف، `sort=-cost_rial`، `-requests` یا برای مدیر `-tokens` و در دفتر `sort=-created_at` یا `amount_rial` کاربرد دارند. `interval=day|week|month` برای روند است. مالکیت از نشست خوانده می‌شود. CSRF در عملیات نوشتن برقرار است. مرورگر در رویدادهای start، model_done و model_error موجودی نسخه‌دار می‌گیرد؛ در پایان و پس از اتصال مجدد اطلاعات حساب از سرور بازخوانی می‌شود.

## ارتقای نصب موجود

۱. از ریشهٔ مخزن و با همان فایل محیطی و volumeهای نصب فعلی کار کنید. ارسال‌های فعال را به پایان برسانید، ورود درخواست تازه را متوقف کنید و از PostgreSQL پشتیبان قابل بازیابی بگیرید. `docker compose down -v` داده‌های volume را حذف می‌کند. اگر هنوز migration شمارهٔ `0003` اجرا نشده، پیش از مهاجرت، `LLM_BASE_URL` و ارجاع قدیمی `LLM_API_KEY` را در محیط Backend بررسی کنید.

۲. نسخهٔ سازگار هر سه سرویس را بسازید. اگر توکنایزر محلی نصب است، به فرمان build گزینهٔ `--build-arg INSTALL_LOCAL_TOKENIZERS=1` بدهید و volume فقط‌خواندنی آن را حفظ کنید. Django با فرمان `migrate` وابستگی‌ها را به‌ترتیب اعمال می‌کند.

```sh
git pull --ff-only origin main
docker compose build backend cleanup web
docker compose stop web backend cleanup
docker compose up -d db
docker compose run --rm backend python manage.py migrate
docker compose run --rm backend python manage.py showmigrations portal
docker compose run --rm backend python manage.py collectstatic --noinput
docker compose run --rm backend python manage.py audit_billing
docker compose up -d backend cleanup web
```

| مهاجرت‌ها به ترتیب | اثر روی داده‌های قبلی |
| --- | --- |
| `0001–0002` | جداول پایه و آمار مصرف هر مدل را ایجاد می‌کنند. |
| `0003` | مدل‌های واقعی قبلی به اتصال پیش‌فرض با آدرس محیط و نام متغیر کلید متصل می‌شوند. مدل‌های نمایشی بدون اتصال می‌مانند. پس از آن، آدرس در Admin مدیریت می‌شود. |
| `0004–0005` | وضعیت درخواست و ارتباط پاسخ با سؤال ثبت می‌شود. پرسش‌های قدیمی بدون پاسخ موفق از Context بعدی کنار می‌روند. |
| `0006` | فیلدهای Thinking و مصرف اضافه می‌شوند. مجموع مصرف معلوم از شمارنده‌های موجود به دست می‌آید. استدلال و تفکیک قدیمی نامعلوم باقی می‌مانند. |
| `0007` | فقط کاربران فاقد Account حساب پیش‌فرض می‌گیرند. مقدارهای تاریخی حساب‌های موجود حفظ می‌شوند. |
| `0008–0009` | کشف مدل و Cache اضافه می‌شود. مدل‌های دستی، Effortها و شناسه‌های قدیمی حفظ می‌شوند. برای شناسهٔ تکراری در یک اتصال، مدیر خطای `existing_duplicates` را بررسی می‌کند. |
| `0010–0011` | زمان پاسخ و پروفایل استدلال اضافه می‌شوند. زمان پاسخ قدیمی نامعلوم است. تنظیمات قدیمی با قرارداد اصلی خوانده می‌شوند. بازگشت به ۰۰۱۰ داده‌های دو ستون پروفایل و انتخاب جدید را حذف می‌کند. |
| `0012` | سؤال‌های قدیمی به ترتیب به پرسش قبلی پیوند می‌خورند. هر پاسخ به همان نسخهٔ سؤال متصل می‌ماند. بازگشت به اسکیمای پیشین، اطلاعات شاخه‌بندی را حذف می‌کند. |
| `0013–0014` | اعتبار اولیهٔ حساب‌های موجود صفر است. تعرفه‌ها و هزینه‌های تاریخی تهی می‌مانند. شمارنده‌های مالی ModelUsage از صفر آغاز می‌شوند و شمارنده‌های توکن قبلی حفظ می‌شوند. |
| `0015–0016` | سنجاق، بازخورد، حداقل خروجی تأییدشده، سقف کاهش‌یافته و ورودی گزارش‌شده از کش را اضافه می‌کنند. سقف و شمارش کش پاسخ‌های قبلی نامعلوم باقی می‌ماند. رزرو مدل‌های موجود به‌صورت پیش‌فرض کامل است. |

برای بازگشت پس از ثبت شاخه، تنظیم استدلال یا مصرف مالی، پایگاه داده و نسخهٔ برنامه را از یک نقطهٔ پشتیبان سازگار بازیابی کنید.

۳. در Admin، تعرفهٔ واقعی فروش هر مدل را وارد کنید. مدل نمایشی تازهٔ `seed_demo` رایگان ساخته می‌شود. برای تخصیص اولیهٔ دسته‌ای به حساب‌های موجودی که قبلاً تخصیص یا اصلاح نداشته‌اند، ابتدا پیش‌نمایش و سپس اجرای صریح زیر در دسترس است. مبلغ فقط یک نمونه است.

```sh
docker compose run --rm backend python manage.py audit_billing --initial-toman 500000
docker compose run --rm backend python manage.py audit_billing --initial-toman 500000 --apply
docker compose run --rm backend python manage.py audit_billing
```

گزینهٔ `--user ID` بررسی یا تخصیص را به یک حساب محدود می‌کند. ممیزی جمع خالص دفتر، رزروهای باز و آمار مالی هر کاربر و مدل را با حساب و ModelUsage می‌سنجد و در صورت اختلاف با کد خطا خارج می‌شود. برای دادهٔ نامعلوم یا بیش‌مصرفی، دفتر را برحسب شناسه بررسی کنید. هرگونه اصلاح باید دلیل و مرجع داشته باشد.
