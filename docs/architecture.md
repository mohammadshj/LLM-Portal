# تصمیم‌های معماری نسخهٔ اولیه

یک Django app برای شروع کافی است. مرزهای HTTP، قوانین کسب‌وکار و ارتباط با مدل در فایل‌های جدا قرار دارند تا بتوان آن‌ها را بدون تغییر کل سامانه توسعه داد.

| بخش | مسئولیت | دلیل انتخاب |
| --- | --- | --- |
| React + TypeScript | رابط، وضعیت گفتگو، انتخاب مدل و گزارش | کامپوننت‌های React، آیکون‌های Lucide و رندر امن Markdown با GFM و Prism |
| Django + DRF | احراز هویت، REST و اعتبارسنجی | استفاده از ORM، User و Admin آماده |
| PostgreSQL | تاریخچه، شمارنده‌ها و قفل ردیفی | کنترل مصرف هم‌زمان بدون سرویس اضافی |
| Nginx | ارائهٔ فایل استاتیک و هدایت API | Node.js فقط در مرحلهٔ build |
| cleanup | بازیابی رزروهای منقضی و پاک‌سازی دوره‌ای تاریخچه | بدون Celery یا Redis برای نگهداری دوره‌ای |

## مسیرهای API

تمام مسیرها به جز csrf، login و health نیازمند نشست معتبر هستند. عملیات تغییردهنده، هدر `X-CSRFToken` می‌خواهند. کلید provider هرگز بخشی از قرارداد مرورگر نیست.

| روش و مسیر | کاربرد |
| --- | --- |
| `GET /api/auth/csrf/` | ایجاد/تازه‌سازی توکن CSRF |
| `POST /api/auth/login/` | نام کاربری و رمز عبور |
| `POST /api/auth/logout/` | پایان نشست |
| `GET /api/auth/me/` | مشخصات کاربر و وضعیت نسخه‌دار اعتبار ریالی |
| `GET /api/models/` | مدل‌های فعال؛ بدون کلید و endpoint |
| `GET/POST /api/conversations/` | فهرست صفحه‌بندی‌شده با فیلتر اختیاری عنوان `q` و وضعیت `is_processing` / ایجاد گفتگو با title |
| `GET /api/conversations/{id}/` | پیام‌های گفتگوی متعلق به کاربر |
| `POST /api/conversations/{id}/` | ارسال content و model_ids؛ پاسخ‌ها و errors هر مدل |
| `POST /api/conversations/{id}/stream/` | ارسال پرسش و دریافت رویدادهای SSE با شناسهٔ درخواست |
| `POST /api/conversations/{id}/requests/{request_id}/cancel/` | درخواست توقف مدل‌های فعال همان ارسال |
| `PATCH /api/conversations/{id}/` | تغییر `title` تا ۱۰۰ نویسه برای مالک گفتگو |
| `DELETE /api/conversations/{id}/` | حذف گفتگو |
| `GET /api/usage/` | آمار کاربران و مدل‌ها، فقط مدیر |
| `GET /api/health/` | سلامت فرایند و اتصال پایگاه داده |

نمونهٔ بدنهٔ ارسال:

```json
{"content": "این موضوع را توضیح بده", "model_ids": [1, 2]}
```

شناسهٔ کاربر را از JSON دریافت نمی‌کنیم؛ مالکیت همیشه از `request.user` تعیین می‌شود. GET، POST، PATCH و DELETE برای گفتگوی دیگران همگی 404 می‌دهند. DRF ورودی خالی، شناسهٔ تکراری، انتخاب بیش از سه مدل و متن بیش از ۱۲۰۰۰ نویسه را رد می‌کند.

## مدل داده

`User → Account` رابطهٔ یک‌به‌یک دارد. هر User چند Conversation و هر Conversation چند Message دارد. پیام دستیار به LanguageModel متصل است. هر مدل واقعی یک ModelConnection دارد که آدرس API و نام متغیر کلید را نگه می‌دارد؛ چند مدل می‌توانند از یک اتصال استفاده کنند. مقدار کلید فقط هنگام فراخوانی از محیط سرور خوانده می‌شود. ModelUsage مصرف هر کاربر برای هر مدل را مستقل از عمر پیام‌ها نگه می‌دارد. FKهای مدل با PROTECT از حذف ناخواستهٔ مشخصات مدل دارای مصرف جلوگیری می‌کنند؛ برای کنارگذاشتن مدل، enabled را خاموش کنید.

## چرخهٔ مقایسه

برای هر مدل، Backend پرسش‌ها و پاسخ‌های تکمیل‌شدهٔ همان مدل را جفت می‌کند. رزرو مجموع بودجه در یک تراکنش کوتاه انجام می‌شود. تماس‌های مستقل با مدل‌ها از راه HTTP ناهمگام اجرا می‌شوند. رویدادهای هر مدل با شناسهٔ درخواست، گفتگو و مدل به کارت مربوط می‌رسند. تسویهٔ هر مدل تراکنش مستقلی دارد. جزئیات در [راهنمای پردازش درخواست](streaming.md) آمده است.

## ادامهٔ توسعه

1. ثبت اتصال‌ها و مدل‌های واقعی در Admin و آزمون قرارداد هر سرویس، به‌ویژه tokenizer و usage. آداپتورهای دارای پروتکل متفاوت در `providers.py` افزوده می‌شوند.
2. اعتبارسنجی توکنایزر محلی اختیاری و حاشیهٔ قالب برای هر مدل.
3. ثبت audit ورود، سیاست قفل حساب و سخت‌سازی استقرار TLS.


پژوهش مدل‌های پزشکی و امتیازهای بنچمارک باید از منابع رسمی و با نسخهٔ دقیق مدل تکمیل شود؛ هیچ امتیاز، اتصال واقعی یا اعتبار بالینی برای دادهٔ نمایشی ادعا نشده است.

هر دو مسیر JSON و SSE از رزرو و تسویهٔ مشترک در services.py استفاده می‌کنند. جدول CreditTransaction دفتر و رویداد پایدار هر تسویه است. APIهای گزارش، قفل‌گذاری و قرارداد حساب در [معماری مالی](billing.md) شرح داده شده‌اند.


## توسعه بدون ساخت مکرر image

یک PostgreSQL محلی یا سرویس PostgreSQL در دسترس لازم است. برای دسترسی از میزبان به DB همین Compose، با یک override محلی پورت `127.0.0.1:5432:5432` را فقط برای سرویس db باز کنید.

```sh
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
# متغیرهای .env را در ترمینال توسعه export کنید؛ Django خودکار .env را نمی‌خواند.
# POSTGRES_HOST=127.0.0.1 و DJANGO_DEBUG=true
.venv/bin/python backend/manage.py migrate
.venv/bin/uvicorn --app-dir backend config.asgi:application --host 127.0.0.1 --port 8000 --reload
# ترمینال دوم:
cd frontend
npm ci
npm run dev
```

Vite درخواست‌های `/api/`، `/admin/` و `/static/` را به Django هدایت می‌کند. CORS و JWT لازم نیست چون مرورگر با یک origin کار می‌کند. در محیط‌هایی که home قابل نوشتن نیست، `npm ci --cache /tmp/portal-npm-cache` به کار ببرید.

برای بررسی سریع مستقل از PostgreSQL، فقط در توسعه و تست می‌توان `PORTAL_SQLITE_TEST=1` داد. SQLite قفل ردیفی PostgreSQL را ندارد و برای اجرای چندکاربره مناسب نیست.

```sh
DJANGO_SECRET_KEY=local-test-only PORTAL_SQLITE_TEST=1 .venv/bin/python backend/manage.py test portal
cd frontend && npm run build
```

## استقرار و فونت

Nginx فایل‌های استاتیک را ارائه می‌کند و PostgreSQL و Backend در شبکهٔ داخلی Compose قرار دارند. برای استقرار عمومی، پراکسی میزبان باید TLS معتبر داشته باشد و Host و Origin واقعی را حفظ کند. محدودسازی ورود در Nginx بر اساس IP است. در صورت افزودن پراکسی، فقط پراکسی‌های مورد اعتماد را برای تشخیص IP کاربر معرفی کنید. در محیط‌های دارای TLS inspection، CA معتبر سازمان را با secret اختیاری BuildKit به نام `proxy_ca` به ساخت image بدهید.

در `frontend/public/fonts/vazirmatn/` فایل `Vazirmatn-Variable.woff2` و مجوز `OFL.txt` قرار دارند. مرورگر فونت را با preload از همان سرور می‌گیرد. یک فایل وزن‌های ۱۰۰ تا ۹۰۰ را پوشش می‌دهد و `font-display: swap` امکان خواندن متن حین دریافت آن را فراهم می‌کند. فونت‌های فرمول‌های ریاضی همراه KaTeX ارائه می‌شوند.

دکمهٔ تغییر تم در صفحهٔ ورود و نوار بالای فضای گفتگو قرار دارد. بدون انتخاب قبلی، تم از تنظیم سیستم پیروی می‌کند و تغییر تنظیم سیستم را دنبال می‌کند. انتخاب دستی در `localStorage` با کلید `portal-theme` ذخیره و میان تب‌ها همگام می‌شود. اگر مرورگر ذخیره‌سازی را مسدود کند، تغییر تم در همان نشست همچنان کار می‌کند. برای بازگشت به پیروی از سیستم، همین کلید را از فضای ذخیرهٔ مرورگر حذف کنید.

`ThemeToggle.tsx` رفتار تغییر تم را نگه می‌دارد و `style.css` رنگ‌ها را از متغیرهای مشترک دو تم می‌گیرد. فایل کوچک `public/theme-init.js` پیش از نمایش React تم ذخیره‌شده را اعمال می‌کند تا صفحهٔ روشن در شروع حالت تیره دیده نشود؛ این فایل خارجی با سیاست `script-src 'self'` سازگار است. Django Admin ابزار داخلی و انتخاب تم مستقل خودش را دارد.
