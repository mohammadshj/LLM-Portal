# Thinking در LLM Portal

برای مدل‌هایی که از Admin همگام می‌شوند، مقدارهای Effort از Metadata یا Registry معتبر می‌آیند. مثال‌های دستی این صفحه همچنان برای اتصال‌هایی که قرارداد آن‌ها تأیید شده قابل استفاده‌اند. [راهنمای کشف مدل و منبع هر قابلیت](discovery.md)


این راهنما برای API متنی OpenAI-compatible و مسیر Chat Completions است. انتخاب Thinking مستقل از انتخاب سرویس و کلید است. ارتقا مدل تازه‌ای ثبت نمی‌کند و برای مدل‌های قبلی پارامتر جدیدی به درخواست اضافه نمی‌کند.

## قرارداد مدل‌ها و اعتبار منابع

در بررسی ۲۰ نوامبر ۲۰۲۶ مستندات منتشرشده در مخازن رسمی Z.ai و Moonshot خوانده شدند. پروکسی محیط برای سایت‌های مستندات تجاری و کارت‌های Hugging Face پاسخ ۴۰۳ داد. جدول زیر شناسه‌ها و تنظیمات کاتالوگ عمومی را برای تطبیق با پنل یا فهرست مدل‌های **همان endpoint** نشان می‌دهد. شناسهٔ بازاریابی یا نام وزن‌های دانلودی جای شناسهٔ API را نمی‌گیرد. نسخه‌های دیگر این خانواده‌ها می‌توانند قرارداد متفاوتی داشته باشند.

## افزودن مدل در Django Admin

1. یک ModelConnection با آدرس پایه و **نام متغیر محیطی** کلید انتخاب یا ایجاد کنید.
2. در LanguageModel شناسهٔ upstream، Context، سقف مستند خروجی سرویس (`provider_output_limit`) و بودجهٔ عملیاتی کوچک‌تر (`max_output_tokens`) را تنظیم کنید. فیلد `output_parameter` تعیین می‌کند بودجه با نام `max_tokens` یا `max_completion_tokens` ارسال شود. هر دو بخش تولید از یک بودجه استفاده می‌کنند. برای اتصال فاقد `stream_options` گزینهٔ `stream_usage_option` را خاموش کنید. Streaming همچنان فعال می‌ماند.
3. قرارداد و زیرمجموعهٔ سطوح مجاز و یک پیش‌فرض از همان زیرمجموعه را انتخاب کنید. `none` قابلیت را غیرفعال می‌کند. `always` برای Thinking اجباری بدون پارامتر کنترلی و `toggle` برای On/Off ساده است. قراردادهای دارای effort و قالب Kimi در جدول و توضیحات بالا آمده‌اند. سطوح و پیش‌فرض برای اتصال‌های جدید با همین پروتکل‌ها بدون تغییر کد قابل تعریف‌اند. پروتکل کاملاً تازه به آداپتور نیاز دارد.
4. سیاست استدلال را مطابق قرارداد سرویس تنظیم کنید. `hidden` متن را نمایش یا ذخیره نمی‌کند. `live` فقط تا پایان نمایش زنده نگه می‌دارد. `store` متن را در تاریخچه نگه می‌دارد. `preserve` همچنین بازفرستادن آن برای همان مدل و مقصد را مجاز می‌کند. فعال‌سازی سیاست به تصمیم مدیر و مجوز سازمان و ارائه‌دهنده بستگی دارد.
5. در فرم چت، برای هر مدل انتخابی سطح مستقلی تعیین کنید. مرورگر نگاشت شناسهٔ محلی به کنترل‌های انتخاب‌شده را می‌فرستد. Backend تعلق شناسه‌ها به همان ارسال و سطح مجاز را پیش از رزرو بررسی می‌کند. خطا موجب تماس با سرویس نمی‌شود.

نمونهٔ بدنهٔ مشترک REST و SSE با شناسه‌های محلی فرضی:

```json
{"content":"این مسئله را حل کن","model_ids":[12,15],"reasoning":{"12":{"toggle":false},"15":{"effort":"max"}}}
```

## نمایش، نگهداری و تاریخچه

`reasoning_delta` و `delta` شناسه‌های یکسان گفتگو، درخواست و مدل دارند. React اولی را به بخش تاشوی استدلال و دومی را به پاسخ اصلی اضافه می‌کند. هر دو به شکل متن رندر می‌شوند. وقتی یک endpoint غیرجریانی JSON می‌دهد، دو بخش پس از دریافت JSON کامل در دسترس‌اند.

تسویه، سطح انتخاب‌شده، متن مجاز، وضعیت و مصرف هر کارت را ثبت می‌کند. لغو و خطا متن جزئی مجاز را حفظ می‌کنند. سؤال و پاسخ موفق هر مدل تنها تاریخچهٔ همان شاخه را تشکیل می‌دهند. در `preserve` متن استدلال بدون خلاصه‌سازی به پیام دستیار اضافه می‌شود. اتصال، آدرس و شناسهٔ upstream برای بازپخش کنترل می‌شوند. اگر تاریخچهٔ قدیمی اطلاعات لازم را ندارد یا مقصد عوض شده، ارسال پیام تازه در آن گفتگو با توضیح رد می‌شود. Tool Calling در این پورتال فعال نیست. پاسخ ابزار یا خروجی ناتمام به دلیل طول، وارد Context موفق نمی‌شود.

سیاست پاک‌سازی ۳۰روزه شامل استدلال ذخیره‌شده نیز می‌شود. نشست و مالکیت گفتگو برای خواندن تاریخچه یا توقف الزامی است. اندازهٔ یک خط یا رویداد SSE محدود است. هر پاسخ تا ۳۲ MiB دادهٔ انتقال، JSON تا ۸ MiB و متن ترکیبی قابل نمایش تا ۴ MiB پذیرفته می‌شود. اتصال بالادست با `Accept-Encoding: identity` باز می‌شود. در قطع سخت فرایند، دادهٔ هنوز تسویه‌نشده می‌تواند از دست برود و بازیابی رزرو مصرف را نامعلوم علامت می‌زند.

## مصرف و رزرو

- **رزرو** شامل تخمین ورودی واقعی ارسال‌شده (از جمله استدلال بازپخش‌شده)، حاشیهٔ قالب پیام و حداکثر خروجی است. هر مدل جداگانه رزرو و تسویه می‌شود. این مقدار سهمیهٔ موقت است.
- **گزارش سرویس** از `prompt_tokens/completion_tokens` یا `input_tokens/output_tokens` و `total_tokens` خوانده می‌شود. اگر مجموع و یک جزء معتبر باشد، جزء دیگر از تفاضل به دست می‌آید. اگر فقط جمع گزارش شود، کل آن ثبت و تسویه می‌شود و تفکیک ورودی/خروجی نامعلوم می‌ماند. اگر فقط ورودی یا خروجی موجود باشد، همان جزء با منبع واقعی حفظ می‌شود. در حضور متن قابل شمارش فقط جزء مفقود برآورد می‌شود. در نبود متن، جزء مفقود و مجموع نامعلوم می‌مانند و تسویه به شمارش‌های موجود محدود می‌شود. گزارش ناسازگار مبنای تسویهٔ واقعی قرار نمی‌گیرد.
- `completion_tokens_details.reasoning_tokens` یا `output_tokens_details.reasoning_tokens` زیرمجموعهٔ خروجی است. دادهٔ معتبر جدا نمایش داده می‌شود و هیچ‌گاه دوباره به مجموع اضافه نمی‌شود. مستقل از نام مدل، در نبود فیلد معتبر عدد استدلال نامعلوم است.
- **تخمینی** یعنی گزارش معتبر موجود نبوده و متن قابل شمارش دریافت شده است. برای تخمین خروجی، بایت‌های پاسخ نهایی و شمارش گزارش‌شدهٔ استدلال در نظر گرفته می‌شوند. در نبود شمارش استدلال، بایت‌های استدلال مجازِ دریافت‌شده به برآورد کمک می‌کنند. خود تعداد توکن‌های استدلال فقط از گزارش معتبر نمایش داده می‌شود. اگر دادهٔ کافی موجود نباشد، مصرف **نامعلوم** است. مبلغ دلاری محاسبه نمی‌شود. در حالت گزارش بیش از رزرو، آمار مدل و پیام کل رقم را حفظ می‌کنند و کسر از سهمیهٔ محلی طبق سیاست موجود حداکثر برابر رزرو همان پاسخ است.
- **توکنایزر محلی** اختیاری است. برای استفاده، هنگام build بک‌اند `--build-arg INSTALL_LOCAL_TOKENIZERS=1` بدهید، پوشهٔ دارای فایل تأییدشدهٔ همان نسخه را با volume فقط‌خواندنی به `/opt/portal/tokenizers` وصل کنید و نام پایهٔ فایل `NAME.json` را در `tokenizer_name` بنویسید. پورتال فایل را محلی می‌خواند. در نبود نام، UTF‑8 و حاشیهٔ `framing_tokens` به کار می‌روند. نام تنظیم‌شده با فایل مفقود درخواست را پیش از تماس رد می‌کند. شمارش محلی فیلدهای متنی با حاشیهٔ قالب همچنان تخمین رزرو است. صحت tokenizer و حاشیه باید با قالب واقعی endpoint سنجیده شود.

## ارتقا و عیب‌یابی

Migration شمارهٔ `0006_thinking_and_token_usage` ستون‌های قابلیت مدل، استدلال و مصرف پیام و آمار مجموع فاقد تفکیک را اضافه می‌کند. برای پیام‌های قدیمی با منبع مصرف معلوم، مجموع از ورودی و خروجی موجود پر می‌شود. استدلال و شمارش جداگانهٔ قدیمی نامعلوم می‌مانند. پس از پایان درخواست‌های فعال و تهیهٔ پشتیبان پایگاه داده، از ریشهٔ پروژه اجرا کنید.

```sh
docker compose build backend cleanup web
docker compose stop web backend cleanup
docker compose run --rm backend python manage.py migrate
docker compose up -d backend cleanup web
docker compose exec backend python manage.py showmigrations portal
```

برای HTTP 400، شناسهٔ واقعی مدل، قرارداد Thinking، نام پارامتر بودجه و پشتیبانی از stream options را بررسی کنید. برای استدلال خالی، سیاست مدل، Off بودن و وجود فیلد در قرارداد API را بررسی کنید. برای `output_limit`، بودجهٔ خروجی و فضای باقی‌ماندهٔ Context را مقایسه کنید. با `docker compose logs --since 5m backend` کد دسته‌بندی خطا و شناسهٔ محلی مدل و اتصال را پیدا کنید. پنل و لاگ برای عیب‌یابی به متن پرسش، استدلال یا کلید نیاز ندارند.

## پروفایل قابلیت استدلال

در نسخهٔ ۰۰۱۱ مسیر کشف قبلی که فقط فهرست Effort را به اجرا می‌رساند با یک پروفایل مشترک برای Admin، API و ارسال جایگزین شده است. `resolve` شواهد همان مدل و اتصال را ترکیب می‌کند. `build_profile` از نتیجه، کنترل‌های قابل استفاده را می‌سازد. هر عضو `WIRE` فقط قطعهٔ JSON مجاز قرارداد خودش را می‌سازد. بدنهٔ گفتگو، نشانی مقصد و کلید اتصال در اختیار این قراردادها قرار نمی‌گیرند.

`GET /api/models/` برای هر مدل `reasoning_profile` برمی‌گرداند. `supported` و `mandatory` می‌توانند true، false یا null باشند. `mode` یکی از `none`، `unknown`، `fixed`، `toggle`، `effort`، `budget` و `combined` است. مدل با پشتیبانی معلوم و روش تنظیم نامعلوم می‌تواند `supported=true, mode=unknown` داشته باشد. `available=false` یعنی پارامتر الزامی شناسایی شده اما مقدار قابل ارسال در اختیار نیست.

هر عضو `controls` نوع، الزامی‌بودن و در صورت وجود پیش‌فرض و منبع آن را دارد. گزینه‌های Effort مقدار اصلی، برچسب اختیاری و `semantic_level` دارند. UI برای معنای نامعلوم خود مقدار اصلی را نشان می‌دهد. بودجه با پیش‌تنظیم یا بازهٔ صحیح محدود به سقف خروجی مدل نمایش داده می‌شود. `exclusive` کنترل‌هایی را مشخص می‌کند که انتخاب یکی انتخاب دیگر را کنار می‌زند.

نمونهٔ بدنه برای دو مدل در مسیر JSON یا SSE:

```json
{"content":"مسئله را بررسی کن","model_ids":[12,15],"reasoning":{"12":{"toggle":true,"effort":"custom-depth"},"15":{"budget":256}}}
```

انتخاب خالی `{}` برای مدل با کنترل‌های اختیاری، پارامتر استدلالی به سرویس نمی‌فرستد. UI پیش‌فرض تأییدشدهٔ مدیر را مقداردهی اولیه می‌کند و پیش‌فرض اختیاری کاتالوگ را به سرویس واگذار می‌کند. تنظیم مدل‌ها مستقل است. Backend مقادیر بولی، رشته و عدد صحیح، حدود بودجه، قرارداد، پارامتر الزامی و تعارض انتخاب‌ها را قبل از رزرو می‌سنجد. تاریخچهٔ پاسخ‌های جدید انتخاب مؤثر را در `reasoning_settings` دارد. فرمت رشته‌ای `thinking` و فیلدهای قبلی مدل و پیام برای کلاینت‌های قدیمی در دسترس‌اند. ارسال هر دو فرمت برای یک شناسه خطای ۴۰۰ دارد.

| قرارداد Chat Completions | پارامتر |
| --- | --- |
| `always` / `none` | بدون پارامتر |
| `effort` / `native_effort` | `reasoning_effort` با رشتهٔ دقیق مدل |
| `toggle` | `thinking.type` |
| `toggle_effort` | `thinking.type` و هنگام فعال بودن `reasoning_effort` |
| `budget_tokens` | `thinking.type=enabled` و `thinking.budget_tokens` |
| `thinking_controls` | زیرمجموعهٔ تأییدشدهٔ Toggle، Effort و Budget |
| `router_effort` | `reasoning.enabled`، `reasoning.effort` یا `reasoning.max_tokens` با کنترل تعارض بودجه و سطح |
| `kimi_preserved` | `thinking.type=enabled`، `thinking.effort` و `thinking.keep=all` همراه سیاست تاریخچهٔ preserve |

برای افزودن قرارداد Chat Completions، نوع‌های کنترل و تابع ساخت قطعهٔ بدنه را در `reasoning_contracts.WIRE` ثبت کنید. در صورت داشتن Metadata مستند، استخراج آن را در `catalog_metadata.py` اضافه کنید. تست قرارداد باید بدنهٔ دقیق و ورودی‌های مردود را پوشش دهد. افزودن پروتکل بومی مانند Anthropic Messages یا Gemini GenerateContent مستلزم آداپتور انتقال مستقل برای URL، احراز هویت، تاریخچه، پاسخ JSON، SSE، مصرف و لغو است. پورتال فعلاً inference را از مسیر Chat Completions انجام می‌دهد.

Migration افزایشی `0011_reasoning_profiles` دو فیلد JSON برای Overrideهای مجزا و انتخاب هر پاسخ می‌سازد. تنظیمات قدیمی هنگام خواندن با قرارداد اصلی به پروفایل تبدیل می‌شوند. این کار به بازنویسی تاریخچه یا استنباط معنای سطوح قدیمی نیاز ندارد. بازگشت به ۰۰۱۰ ستون‌های جدید و داده‌های ثبت‌شده در آن دو ستون را حذف می‌کند. برای بازگشت با حفظ انتخاب‌های جدید ابتدا از پایگاه داده پشتیبان بگیرید.
