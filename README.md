# LLM Portal — پورتال مدل‌های زبانی

نسخهٔ اولیهٔ اختصاصی با Python 3.12، Django 5.2 LTS، DRF، PostgreSQL 17 و React 19 / TypeScript / Vite. رابط فارسی، RTL و واکنش‌گراست. Frontend در زمان ساخت به فایل استاتیک تبدیل می‌شود؛ محیط استقرار هیچ پردازش Node.js ندارد.

راهنمای تکمیلی: [تصمیم‌های معماری و API](docs/architecture.md) · [نتایج آزمون‌ها](docs/validation.md)

## قابلیت‌های فعلی

- ورود کاربران ایجادشده توسط مدیر، نشست Django، CSRF و خروج؛ ثبت‌نام عمومی نداریم.
- انتخاب حداکثر سه مدل، ارسال پرسش مشترک و نمایش پاسخ‌های نام‌گذاری‌شده؛ هر مدل در ادامه فقط پاسخ‌های قبلی خودش را می‌بیند.
- تاریخچهٔ اختصاصی هر کاربر با جست‌وجوی عنوان در تمام صفحه‌ها، تغییر نام و حذف با تأیید.
- اعتبار تومانی، تعرفهٔ مستقل هر مدل و رزرو و تسویهٔ اتمیک برای هر پاسخ.
- مدیریت اعتبار و تعرفه در Django Admin، گزارش مالی شخصی و داشبورد کاربر × مدل برای مدیر.
- حذف دوره‌ای گفتگوهای قدیمی‌تر از ۳۰ روز؛ شمارنده‌های مصرف با حذف تاریخچه حفظ می‌شوند.
- دو مدل **نمایشی** بدون اینترنت برای آزمون؛ آداپتور Chat Completions سازگار با OpenAI برای اتصال واقعی.

این نسخه تحویل نهایی تمام تعهدات دو PDF نیست. اتصال واقعی به دو ارائه‌دهنده، استقرار یک مدل پزشکی، پژوهش و بنچمارک‌ها، گزارش رویدادهای امنیتی و سخت‌سازی نهایی هنوز انجام نشده‌اند. سندهای ضمیمه منبع نیازمندی هستند؛ زمان‌بندی، قرارداد و تخصیص نیروی انسانی آن‌ها دستور اجرایی پروژه محسوب نمی‌شوند.

## اجرای Docker

از ریشهٔ مخزن:

```sh
cp .env.example .env
# .env را ویرایش کنید؛ دو مقدار مستقل و تصادفی برای SECRET_KEY و PASSWORD قرار دهید.
# برای توسعهٔ HTTP محلی: DJANGO_DEBUG=true
# برای تولید: DJANGO_DEBUG=false و دامنه‌ها و CSRF_TRUSTED_ORIGINS واقعی
chmod 600 .env
docker compose build
docker compose up -d db
docker compose run --rm backend python manage.py migrate
docker compose run --rm backend python manage.py collectstatic --noinput
docker compose run --rm backend python manage.py createsuperuser
# اختیاری، فقط برای آزمایش:
docker compose run --rm backend python manage.py seed_demo
docker compose up -d
```

پورت داخلی وب 8080 است و تنها به loopback سرور متصل است. سرویس Backend و PostgreSQL پورت عمومی ندارند. برای استفاده روی سرور لینوکسی، یک reverse proxy میزبان با TLS معتبر را مقابل پورت 8080 قرار دهید و Host و Origin واقعی را حفظ کنید. تا تنظیم HTTPS از کوکی امن در حالت تولید انتظار ورود روی HTTP نداشته باشید. پروژه گواهی TLS ساختگی تولید نمی‌کند.

کنترل سلامت و تست‌ها:

```sh
curl --fail http://127.0.0.1:8080/api/health/
docker compose exec backend python manage.py test portal
docker compose exec web nginx -t
```

`health` اتصال پایگاه داده را بررسی می‌کند. در محیط‌های دارای TLS inspection، Dockerfileها secret اختیاری BuildKit به نام `proxy_ca` را می‌پذیرند؛ CA باید از محیط معتبر به build داده شود. تأیید TLS را غیرفعال نکنید.

ساخت image، اجرای migration و collectstatic عمداً جدا هستند؛ روی هر راه‌اندازی مهاجرت پایگاه داده انجام نمی‌دهیم. پس از تغییر سورس `docker compose build` و `docker compose up -d` را اجرا کنید. از volume پایگاه داده نسخهٔ پشتیبان بگیرید؛ `down -v` داده‌ها را حذف می‌کند.

## توسعه بدون ساخت مکرر image

یک PostgreSQL محلی یا سرویس PostgreSQL در دسترس لازم است. برای دسترسی از میزبان به DB همین Compose، با یک override محلی پورت `127.0.0.1:5432:5432` را فقط برای سرویس db باز کنید.

```sh
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
# متغیرهای .env را در ترمینال توسعه export کنید؛ Django خودکار .env را نمی‌خواند.
# POSTGRES_HOST=127.0.0.1 و DJANGO_DEBUG=true
.venv/bin/python backend/manage.py migrate
.venv/bin/uvicorn --app-dir backend config.asgi:application --host 127.0.0.1 --port 8000 --reload
# ترمینال دوم:
cd frontend
npm ci
npm run dev
```

Vite درخواست‌های `/api/`، `/admin/` و `/static/` را به Django هدایت می‌کند. CORS و JWT لازم نیست چون مرورگر با یک origin کار می‌کند. در محیط‌هایی که home قابل نوشتن نیست، `npm ci --cache /tmp/portal-npm-cache` به کار ببرید.

برای بررسی سریع مستقل از PostgreSQL، فقط در توسعه و تست می‌توان `PORTAL_SQLITE_TEST=1` داد. SQLite قفل ردیفی PostgreSQL را ندارد و برای اجرای چندکاربره مناسب نیست.

```sh
DJANGO_SECRET_KEY=local-test-only PORTAL_SQLITE_TEST=1 .venv/bin/python backend/manage.py test portal
cd frontend && npm run build
```

## فونت و حالت نمایش

فایل‌های وزیرمتن در `frontend/public/fonts/vazirmatn/` همراه مجوز SIL OFL نگهداری می‌شوند. رابط پورتال نسخهٔ Variable را از همان سرور بارگذاری می‌کند؛ نصب فونت روی دستگاه کاربر یا اتصال به سرویس فونت خارجی لازم نیست. تنها یک فایل برای وزن‌های ۱۰۰ تا ۹۰۰ بارگیری می‌شود؛ متن عادی ۴۰۰، عنوان خوشامد ۵۰۰، سرستون جدول ۶۰۰ و متن برجسته/عنوان‌ها ۷۰۰ هستند. سایر فایل‌های ارسالی برای استفادهٔ بعدی در پروژه حفظ شده‌اند. `font-display: swap` هنگام دریافت فونت اجازهٔ نمایش فوری متن را می‌دهد.

دکمهٔ تغییر تم در صفحهٔ ورود و نوار بالای فضای گفتگو قرار دارد. بدون انتخاب قبلی، تم از تنظیم سیستم پیروی می‌کند و تغییر تنظیم سیستم را دنبال می‌کند. انتخاب دستی در `localStorage` با کلید `portal-theme` ذخیره و میان تب‌ها همگام می‌شود. اگر مرورگر ذخیره‌سازی را مسدود کند، تغییر تم در همان نشست همچنان کار می‌کند. برای بازگشت به پیروی از سیستم، همین کلید را از فضای ذخیرهٔ مرورگر حذف کنید.

`ThemeToggle.tsx` رفتار تغییر تم را نگه می‌دارد و `style.css` رنگ‌ها را از متغیرهای مشترک دو تم می‌گیرد. فایل کوچک `public/theme-init.js` پیش از نمایش React تم ذخیره‌شده را اعمال می‌کند تا صفحهٔ روشن در شروع حالت تیره دیده نشود؛ این فایل خارجی با سیاست `script-src 'self'` سازگار است. Django Admin ابزار داخلی و انتخاب تم مستقل خودش را دارد.

## کار با میز گفتگو

از «گفتگوی تازه» شروع کنید. با «انتخاب مدل» می‌توانید نام مدل را جست‌وجو کنید و یک تا سه مدل را انتخاب کنید. «تنظیمات استدلال» سطح‌های مجاز هر مدل را از API می‌خواند. روی رایانه Enter پیام را می‌فرستد و Shift+Enter خط جدید می‌سازد. روی دستگاه لمسی از دکمهٔ ارسال استفاده کنید.

در نمایش عریض، پاسخ‌های یک ارسال کنار هم قرار می‌گیرند. در فضای باریک با دکمهٔ نام مدل بین پاسخ‌ها جابه‌جا شوید. از «گسترش پاسخ» برای مطالعهٔ متن طولانی استفاده کنید. استدلال و جزئیات مصرف هر مدل جداگانه باز می‌شوند. با اسکرول به عقب می‌توانید هنگام تولید پاسخ، پیام‌های قبلی را بخوانید. «آخرین پیام» دنبال‌کردن جریان را از سر می‌گیرد.

منوی سه‌نقطهٔ کنار عنوان هر گفتگو، تغییر نام و حذف را در دسترس می‌گذارد. اعتبار مالی نوار کناری از حساب کاربر خوانده می‌شود. جزئیات مصرف هر پاسخ، مقادیر گزارش‌شده، تخمینی و نامعلوم را از هم مشخص می‌کند. دکمهٔ ارسال مجدد در کارت ناموفق یا متوقف‌شده، سؤال را برای بازبینی در کادر پیام قرار می‌دهد.

برای ارتقای نصب موجود به رابط جدید، از ریشهٔ مخزن اجرا کنید. این تغییر به migration جدید نیاز ندارد.

```sh
docker compose up -d --build backend web
```

## کشف خودکار مدل‌ها

در Django Admin اتصال را با نوع Provider، Base URL و نام متغیر محیطی کلید ذخیره کنید. در فرم ویرایش، **Sync Models** فهرست را دریافت می‌کند. مدل‌های تازه پس از بازبینی مدیر فعال می‌شوند. جدول هر مدل قابلیت‌ها، منبع آن‌ها و Effortهای قابل تنظیم را نشان می‌دهد. تطبیق دقیق با Models.dev، Cache آفلاین، Override دستی و دستورهای ارتقای ۰۰۰۸ و ۰۰۰۹ در [راهنمای کشف مدل](docs/discovery.md) آمده است.

## مدیریت مدل و اعتبار تومانی

### ساخت و ویرایش کاربران

با مدیر ساخته‌شده توسط `createsuperuser` وارد `/admin/` شوید. از بخش احراز هویت، **کاربران ← افزودن کاربر** را باز کنید. نام کاربری و رمز عبور را وارد کنید، نقش را انتخاب کنید و برای دسترسی فوری، «فعال» را علامت بزنید.

| انتخاب فرم | دسترسی |
| --- | --- |
| **User — کاربر** | ورود به پورتال، گفتگو با مدل‌های فعال، مشاهدهٔ تاریخچه و اعتبار خودش |
| **Admin — مدیر** | همهٔ امکانات کاربر، پنل Django، ساخت مدیر یا کاربر، مدیریت مدل‌ها، اتصال‌ها، سهمیه و گزارش مصرف |

نقش Admin هر دو پرچم استاندارد `is_staff` و `is_superuser` را فعال می‌کند. نقش User هر دو را غیرفعال می‌کند. حساب‌های قدیمی که فقط یکی از پرچم‌ها را دارند، تا تعیین صریح نقش Admin، در پورتال دسترسی کاربر عادی دارند. مدیر می‌تواند اطلاعات شخصی یا نقش را در صفحهٔ همان کاربر و رمز را از پیوند تغییر رمز Django ویرایش کند.

در فرم ایجاد، «اعتبار اولیه» را به تومان وارد کنید. فیلد خالی از پیش‌فرض مدیریتی استفاده می‌کند. در صفحهٔ کاربر «تغییر اعتبار» را انتخاب کنید. در فرم هر مدل، تعرفهٔ ورودی و خروجی برای یک میلیون توکن را جداگانه تنظیم کنید. مقدار صفر رایگان و مقدار خالی نیازمند تعیین تعرفه است. راهنمای ارتقا، رزرو، بازپرداخت، گزارش و تطبیق دفتر در [مستند اعتبار تومانی](docs/billing.md) آمده است.

### غیرفعال‌سازی و فعال‌سازی مجدد

در صفحهٔ کاربر، علامت **فعال** را بردارید و ذخیره کنید. فهرست کاربران وضعیت فعال را نشان می‌دهد و فیلتر فعال/غیرفعال دارد. پس از ثبت تغییر، ورود جدید و دسترسی نشست جاری به APIهای محافظت‌شده مسدود می‌شود. Django وضعیت کاربر را در هر درخواست از پایگاه داده می‌خواند. برای بازگرداندن دسترسی، «فعال» را دوباره علامت بزنید. نشست قبلی که هنوز معتبر است ممکن است پس از فعال‌سازی مجدد قابل استفاده باشد.

غیرفعال‌سازی از پنل برای ارسال‌های در حال اجرا درخواست توقف ثبت می‌کند. ناظر جریان هر ۰٫۷۵ ثانیه وضعیت توقف را بررسی می‌کند. دادهٔ از قبل ارسال‌شده یا در مسیر ممکن است به مرورگر برسد. پاسخ تکمیل‌شده محفوظ است و مدل در حال تولید با همان سیاست Stop تسویه می‌شود. متن جزئی مجاز و مصرف گزارش‌شده یا برآوردی ثبت و رزرو آزاد می‌شود. زمان قطع اتصال لزوماً با پایان هزینه در سرویس خارجی یکسان نیست. فعال‌سازی فوری یک ارسال متوقف‌شده را از سر نمی‌گیرد.

Account و آمار مصرف پس از غیرفعال‌سازی باقی می‌مانند. سیاست عادی ۳۰روزهٔ نگهداری گفتگوها برای حساب فعال و غیرفعال یکسان است.

### ارتقا از نسخهٔ Thinking

پس از پشتیبان‌گیری از PostgreSQL و پایان ارسال‌های فعال، در ریشهٔ پروژه اجرا کنید. در نصب‌هایی که tokenizer محلی دارند، همان گزینهٔ ساخت `--build-arg INSTALL_LOCAL_TOKENIZERS=1` را حفظ کنید.

```sh
git pull --ff-only origin main
docker compose build backend cleanup
docker compose stop backend cleanup
docker compose run --rm backend python manage.py migrate
docker compose up -d backend cleanup
docker compose exec backend python manage.py showmigrations portal
```

Migration داده‌ای `0007_backfill_accounts` برای کاربران فاقد Account یک رکورد با سهمیهٔ پیش‌فرض می‌سازد. رکوردهای موجود سهمیه و مصرف قبلی خود را نگه می‌دارند.

### افزودن سرویس و مدل‌های جدید

دیگر یک کلید مشترک اجباری برای تمام مدل‌ها نداریم. در Admin، بخش **اتصال‌های سرویس مدل** (`ModelConnection`) آدرس API و **نام متغیر محیطی کلید** را نگه می‌دارد. هر `LanguageModel` به یک اتصال اشاره می‌کند. تعداد اتصال‌ها و مدل‌های ثبت‌شده سقف ثابت نرم‌افزاری ندارد؛ محدودیت هر درخواست مقایسه همچنان حداکثر سه مدل است.

مثال تنظیمات سرور (مقادیر واقعی را فقط در `.env` وارد کنید):

```dotenv
LLM_OPENAI_API_KEY=
LLM_OPENROUTER_API_KEY=
```

سپس در Admin دو اتصال بسازید:

| نام اتصال | base_url | api_key_env |
| --- | --- | --- |
| سرویس OpenAI | `https://api.openai.com/v1` | `LLM_OPENAI_API_KEY` |
| سرویس OpenRouter | `https://openrouter.ai/api/v1` | `LLM_OPENROUTER_API_KEY` |

برای هر مدل، `provider=openai` (یعنی **پروتکل سازگار با OpenAI**)، اتصال مناسب، `model_id` دقیق طبق مستندات همان سرویس، context window و سقف خروجی را انتخاب کنید. چند مدل می‌توانند یک اتصال و یک کلید داشته باشند؛ حتی دو مدل با model_id یکسان می‌توانند از دو اتصال مستقل استفاده کنند. نام نمایشی مدل‌ها را متمایز انتخاب کنید تا مقایسه روشن بماند.

- افزودن مدل به اتصال موجود: فقط ثبت در Admin؛ تغییر کد، متغیر محیطی و build Frontend لازم نیست.
- افزودن سرویس مستقل: متغیر جدیدی مانند `LLM_SERVICE3_API_KEY` در `.env` تعریف کنید، Backend را recreate کنید و اتصال را در Admin بسازید. نام متغیر باید الگوی `LLM_<NAME>_API_KEY` یا `LLM_API_KEY` داشته باشد. فقط نام متغیر را در Admin بنویسید، نه مقدار کلید.
- سرویس محلی سازگار بدون احراز هویت: مثلاً آدرس `http://host.docker.internal:11434/v1` با api_key_env خالی؛ Backend در این حالت هدر Authorization ارسال نمی‌کند. دسترسی Docker به میزبان باید متناسب با سرور تنظیم شود؛ `localhost` داخل کانتینر خود همان کانتینر است. برای سرویس‌های خارجی از HTTPS استفاده کنید و فقط endpointهای مورد اعتماد ثبت کنید.
- غیرفعال‌کردن اتصال، فراخوانی مدل‌های متصل به آن را متوقف می‌کند. اتصال دارای مدل قابل حذف نیست؛ ابتدا مدل‌ها را به اتصال دیگری منتقل کنید.

تنها آداپتور واقعی فعلی، Chat Completions با `max_tokens` و `usage.prompt_tokens/completion_tokens` است. سرویس‌های دارای قرارداد متفاوت مانند API بومی Anthropic یا Gemini به آداپتور مستقل نیاز دارند؛ افزودن کلید به‌تنهایی آن‌ها را سازگار نمی‌کند. این مثال‌ها به معنی آزمون اتصال واقعی این سرویس‌ها نیستند.

### ارتقا از تنظیم قبلی

migration شمارهٔ `0003` یک «اتصال پیش‌فرض» با آدرس `LLM_BASE_URL` و ارجاع به `LLM_API_KEY` می‌سازد و تمام مدل‌های واقعی قبلی را به آن متصل می‌کند؛ مدل‌های نمایشی بدون اتصال باقی می‌مانند. خود کلید به پایگاه داده منتقل نمی‌شود. پس از این مهاجرت، آدرس هر اتصال در Admin مدیریت می‌شود و تغییر `LLM_BASE_URL` دیگر اتصال ثبت‌شده را تغییر نمی‌دهد.

برای ارتقای نسخهٔ منتشرشده، ابتدا imageها را بسازید. ارسال‌های فعال را پیش از ارتقا به پایان برسانید و پس از migration سرویس‌ها را با همان نسخه بالا بیاورید.

```sh
docker compose build backend cleanup web
docker compose stop web backend cleanup
docker compose run --rm backend python manage.py migrate
docker compose up -d backend cleanup web
```

افزودن/تعویض مقدار کلید در `.env` به recreate Backend نیاز دارد؛ `restart` به‌تنهایی متغیرهای جدید Compose را بارگذاری نمی‌کند. کلیدها نه در API مدل‌ها برگردانده می‌شوند، نه در React و نه در پایگاه داده ذخیره می‌شوند. جزئیات اتصال نیز از API عمومی مدل‌ها پنهان است؛ خطای یک اتصال به کلید اتصال دیگر fallback نمی‌کند.

## ساختار و منطق

- `backend/config/`: تنظیمات محیط، URL و برنامهٔ ASGI؛ PostgreSQL حالت پیش‌فرض.
- `backend/portal/models.py`: جداول Account، ModelConnection، LanguageModel، Conversation، Message و ModelUsage.
- `serializers.py`: قرارداد JSON و اعتبارسنجی ورودی.
- `views.py`: نشست، کنترل دسترسی و مسیرهای REST.
- `services.py`: قوانین گفتگو، سهمیه و شاخه‌های مقایسه. تغییر قواعد کسب‌وکار عمدتاً اینجاست.
- `providers.py`: تنها محل ارتباط با مدل؛ اضافه‌کردن ارائه‌دهنده در این مرز انجام می‌شود.
- `frontend/src/main.tsx` ورود را مدیریت می‌کند. `Workspace.tsx` تاریخچه، گزارش، گفتگو و کادر پیام را به هم متصل می‌کند.
- `useChats.ts` چرخهٔ ارسال را بر اساس شناسهٔ گفتگو و درخواست نگه می‌دارد. `stream.ts` رویدادهای SSE و `api.ts` نشست و CSRF را مدیریت می‌کنند.
- `useHistory.ts` فهرست صفحه‌بندی‌شده و جست‌وجو را می‌خواند. `MessageList.tsx` پاسخ‌ها را بر اساس نوبت گفتگو نمایش می‌دهد. `MarkdownRenderer.tsx` نمایش Markdown و کد را بر عهده دارد.
- `deploy/`: ساخت استاتیک Frontend و تنظیم Nginx؛ `compose.yaml`: چهار سرویس db، backend، web و cleanup.

جریان درخواست: React ← REST/Session → view → service → provider. ORM تاریخچه و مصرف را در PostgreSQL نگه می‌دارد. پاسخ نهایی با React Markdown و افزونهٔ GFM رندر می‌شود. HTML خام و بارگیری تصویر خارجی غیرفعال است. Prism توکن‌های کد را برای رنگ‌آمیزی به عناصر متنی React تبدیل می‌کند. Router، state manager، Redis و صف کار در این مرحله لازم نیستند.

## محدودیت‌های نسخهٔ اولیه

مبلغ رزرو پیش از ارسال بر اساس تعرفهٔ همان لحظه، برآورد ورودی، حاشیهٔ پیام و حداکثر خروجی محاسبه می‌شود. در حالت پیش‌فرض، برآورد ورودی از تعداد بایت UTF-8 استفاده می‌کند. این تخمین برای tokenizerهای byte-BPE محافظه‌کارانه است و ممکن است زودتر از ظرفیت واقعی گفتگو را متوقف کند؛ شمارش دقیق و مدل‌محور هنوز پیاده نشده است. مصرف گزارش‌شدهٔ هر مدل از فیلد usage ثبت می‌شود. در نبود این فیلد، مصرف برآوردی یا نامعلوم در تاریخچه مشخص است. مدل نمایشی از تعداد بایت استفاده می‌کند. قبل از افزودن مدل جدید، tokenizer، قالب پیام و قرارداد usage آن باید اعتبارسنجی شود.

هر گفتگو می‌تواند یک ارسال فعال داشته باشد. در زمان تولید پاسخ می‌توانید گفتگو را عوض کنید، در گفتگوی دیگر پیام بفرستید و به پاسخ در حال تولید برگردید. هر یک از حداکثر سه مدل متن خود را به محض دریافت در کارت همان مدل نشان می‌دهد. دکمهٔ توقف به ارسال جاری همان گفتگو مربوط است. رفتار تاریخچه، سهمیه، قطع ارتباط و راهنمای بررسی خطاهای DeepSeek در [راهنمای درخواست‌های جریانی](docs/streaming.md) آمده است.

«زمان پاسخ» در کارت هر مدل هنگام انتظار و تولید متن به‌روز می‌شود. زمان نهایی از ثبت درخواست مدل در سرور تا پایان جریان، خطا یا توقف اندازه‌گیری می‌شود، شامل زمان استدلال است و با دقت میلی‌ثانیه در تاریخچه ذخیره می‌شود. پاسخ‌های قدیمی زمان ثبت‌شده ندارند.

سرویس cleanup رزروهای منقضی را هر دقیقه بررسی و پاک‌سازی تاریخچه را تقریباً روزی یک بار اجرا می‌کند. گفتگو پس از ۳۰ روز بلافاصله از API مخفی و حداکثر در اجرای بعدی حذف می‌شود. پاک‌سازی backupها سیاست مستقلی می‌خواهد. محدودسازی ورود در Nginx بر مبنای IP برقرار است؛ اگر proxy دیگری جلو آن باشد، برای تشخیص IP واقعی باید trust آن صریحاً تنظیم شود. احراز هویت دومرحله‌ای، audit اختصاصی ورود، قفل حساب و استقرار TLS باید پیش از بهره‌برداری عمومی تکمیل و بازبینی شوند. این سامانه در وضعیت فعلی برای تصمیم‌گیری پزشکی اعتبارسنجی نشده است.

## فرمول‌های ریاضی و نسخه‌های پیام

در سؤال یا پاسخ، فرمول درون‌خطی را با `$...$` یا `\(...\)` و فرمول نمایشی را با `$$...$$` یا `\[...\]` بنویسید. فرمول کامل هنگام دریافت پاسخ با KaTeX نمایش داده می‌شود. کپی پیام، متن اصلی Markdown و LaTeX را برمی‌گرداند. داخل کد می‌توان خود دستورهای LaTeX را نشان داد. فونت‌های ریاضی همراه برنامه ارائه می‌شوند.

با مداد کنار سؤال، متن را ویرایش و «ذخیره و ارسال» را انتخاب کنید. نسخهٔ جدید به‌طور پیش‌فرض از مدل‌ها و تنظیمات استدلال نسخهٔ انتخاب‌شده استفاده می‌کند. برای عوض‌کردن مدل یا تنظیمات، ابتدا کادر ارسال را تنظیم و گزینهٔ مربوط را در ویرایشگر فعال کنید. اگر مدل قبلی غیرفعال شده یا تنظیم آن دیگر معتبر نیست، همین گزینه امکان انتخاب جایگزین را می‌دهد. پیکان چپ نسخهٔ قدیمی‌تر و پیکان راست نسخهٔ جدیدتر را نشان می‌دهد. شمارهٔ ۱ همیشه جدیدترین نسخه است.

هر ویرایش یک درخواست تازه با مصرف مستقل می‌سازد. انتخاب نسخه فقط سؤال، پاسخ‌ها و ادامهٔ ذخیره‌شدهٔ همان شاخه را نمایش می‌دهد. نسخهٔ انتخاب‌شده پس از بارگذاری مجدد صفحه نیز فعال است. تا پایان تولید یا توقف پاسخ، تغییر شاخه در همان گفتگو قفل است. سیاست نگهداری ۳۰ روزه شامل همهٔ شاخه‌های گفتگو می‌شود.

### API و ارتقا

- برای ویرایش، کلاینت در POST فعلی گفتگو یا مسیر SSE، شناسهٔ نسخهٔ فعال سؤال را در `edit_of` می‌فرستد. با حذف `model_ids` مدل‌ها از همان نسخه به ارث می‌رسند. پاسخ جزئیات گفتگو شامل پیام‌های شاخهٔ فعال، `active_leaf` و آرایهٔ شناسه‌های `versions` برای هر سؤال فعال، از جدید به قدیم است.
- مسیر `/api/conversations/{chat}/messages/{question}/versions/` با GET شناسه‌های نسخه‌ها را برمی‌گرداند. POST با `version_id` نسخه را فعال می‌کند و محتوای شاخه را برمی‌گرداند. کلاینت برای ارسال، ویرایش و تغییر نسخه، `expected_leaf` آخرین نمای خود را می‌فرستد. پاسخ ۴۰۹ یعنی گفتگو در حال پردازش است یا نمای کلاینت تغییر کرده و باید تاریخچه دوباره خوانده شود.
- در Migration شمارهٔ `0012_conversation_branches`، سؤال‌های قدیمی به ترتیب به پرسش قبلی پیوند می‌خورند. نسخه‌های یک نوبت، گفتگو و پرسش قبلی مشترک دارند. هر پاسخ با همان `parent` قبلی به نسخهٔ دقیق سؤال متصل می‌ماند. برای ارتقا، از پایگاه داده پشتیبان بگیرید، اجازه دهید درخواست‌های فعال به پایان برسند و دستورهای ساخت، توقف، `migrate` و راه‌اندازی بخش «ارتقا از تنظیم قبلی» را اجرا کنید. در نصب‌های دارای tokenizer محلی، همان گزینهٔ ساخت قبلی را نگه دارید. بازگشت به اسکیمای پیش از ۰۰۱۲ اطلاعات شاخه‌بندی را از بین می‌برد.
- برای توسعهٔ محلی Frontend، در پوشهٔ `frontend` دستورهای `npm ci` و `npm run build` را اجرا کنید.
