# تصمیم‌های معماری نسخهٔ اولیه

یک Django app برای شروع کافی است. مرزهای HTTP، قوانین کسب‌وکار و ارتباط با مدل در فایل‌های جدا قرار دارند تا بتوان آن‌ها را بدون تغییر کل سامانه توسعه داد.

| بخش | مسئولیت | دلیل انتخاب |
| --- | --- | --- |
| React + TypeScript | رابط، وضعیت گفتگو، انتخاب مدل و گزارش | فقط React و React DOM در وابستگی‌های اجرایی |
| Django + DRF | احراز هویت، REST و اعتبارسنجی | استفاده از ORM، User و Admin آماده |
| PostgreSQL | تاریخچه، شمارنده‌ها و قفل ردیفی | کنترل مصرف هم‌زمان بدون سرویس اضافی |
| Nginx | ارائهٔ فایل استاتیک و هدایت API | Node.js فقط در مرحلهٔ build |
| cleanup | اجرای روزانهٔ یک management command | بدون Celery یا Redis برای یک کار دوره‌ای ساده |

## مسیرهای API

تمام مسیرها به جز csrf، login و health نیازمند نشست معتبر هستند. عملیات تغییردهنده، هدر `X-CSRFToken` می‌خواهند. کلید provider هرگز بخشی از قرارداد مرورگر نیست.

| روش و مسیر | کاربرد |
| --- | --- |
| `GET /api/auth/csrf/` | ایجاد/تازه‌سازی توکن CSRF |
| `POST /api/auth/login/` | نام کاربری و رمز عبور |
| `POST /api/auth/logout/` | پایان نشست |
| `GET /api/auth/me/` | مشخصات کاربر و سهمیه |
| `GET /api/models/` | مدل‌های فعال؛ بدون کلید و endpoint |
| `GET/POST /api/conversations/` | فهرست صفحه‌بندی‌شده / ایجاد گفتگو با title |
| `GET /api/conversations/{id}/` | پیام‌های گفتگوی متعلق به کاربر |
| `POST /api/conversations/{id}/` | ارسال content و model_ids؛ پاسخ‌ها و errors هر مدل |
| `DELETE /api/conversations/{id}/` | حذف گفتگو |
| `GET /api/usage/` | آمار کاربران و مدل‌ها، فقط مدیر |
| `GET /api/health/` | سلامت فرایند و اتصال پایگاه داده |

نمونهٔ بدنهٔ ارسال:

```json
{"content": "این موضوع را توضیح بده", "model_ids": [1, 2]}
```

شناسهٔ کاربر را از JSON دریافت نمی‌کنیم؛ مالکیت همیشه از `request.user` تعیین می‌شود. GET، POST و DELETE برای گفتگوی دیگران همگی 404 می‌دهند. DRF ورودی خالی، شناسهٔ تکراری، انتخاب بیش از سه مدل و متن بیش از ۱۲۰۰۰ نویسه را رد می‌کند.

## مدل داده

`User → Account` رابطهٔ یک‌به‌یک دارد. هر User چند Conversation و هر Conversation چند Message دارد. پیام دستیار به LanguageModel متصل است. ModelUsage مصرف هر کاربر برای هر مدل را مستقل از عمر پیام‌ها نگه می‌دارد. FKهای مدل با PROTECT از حذف ناخواستهٔ مشخصات مدل دارای مصرف جلوگیری می‌کنند؛ برای کنارگذاشتن مدل، enabled را خاموش کنید.

## چرخهٔ مقایسه

برای هر مدل، پیام‌های کاربر و فقط جواب‌های قبلی همان مدل جمع می‌شوند. سهمیهٔ لازم برای تمام مدل‌های انتخابی پیش از تماس بررسی می‌شود. پاسخ‌ها به‌ترتیب دریافت می‌شوند و با نام مدل در کارت‌های کنارهم نمایش داده می‌شوند. در موبایل کارت‌ها زیرهم قرار می‌گیرند. خطای provider به پیام عمومی تبدیل می‌شود تا جزئیات پاسخ خارجی یا credential در خروجی نباشد.

در این نسخه انتخاب مدل تازه در میانهٔ گفتگو، تمام پرسش‌های قبلی کاربر را به آن مدل می‌دهد؛ جواب‌های مدل‌های دیگر به آن منتقل نمی‌شود. برای زمینهٔ مستقل کاملاً تازه، گفتگوی جدید بسازید.

## ادامهٔ توسعه

1. تعیین مدل‌ها و endpointهای واقعی و آزمون قرارداد هر provider، به‌ویژه tokenizer و usage.
2. جایگزینی برآورد بایتی با شمارش دقیق مطابق مدل؛ رزرو اعتبار خارج از تراکنش طولانی در صورت افزایش بار.
3. ثبت audit ورود/تغییر سهمیه، سیاست قفل حساب و سخت‌سازی استقرار TLS.
4. در صورت نیاز واقعی، streaming، خروجی Markdown امن و گزارش هزینهٔ پولی با نرخ نسخه‌بندی‌شده.

پژوهش مدل‌های پزشکی و امتیازهای بنچمارک باید از منابع رسمی و با نسخهٔ دقیق مدل تکمیل شود؛ هیچ امتیاز، اتصال واقعی یا اعتبار بالینی برای دادهٔ نمایشی ادعا نشده است.
